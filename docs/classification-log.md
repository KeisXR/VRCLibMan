# 分類記録

確認キューに代わる画面と、その土台の説明です。分類は自動で適用され、誰の承認も待ちません。分類記録は、いつの実行で何をどこへ振り分けたかを後から見るための履歴で、見なくても何も困りません。

## 考え方

- 分類に「利用者が処理しないと溜まり続けるもの」を作りません。ログの未確認件数は [アセットの更新](asset-update-log.md) です。
- 「これはアバターですか？」のような確認や登録の問いかけをしません。名前は同梱の対応表とアバター DB に自動で照合し、あれば結び、なければ結びません。
- DB に無い名前はアプリの中の宿題にせず、「未収録の名前」として事実だけ残します。対応表の欠けは GitHub の Issue で直します。自動投稿はしません。

## 記録するもの

`src-tauri/src/db/classification_log.rs` が、入口ごとに 1 つの実行（`classification_runs`）を作り、商品ごとの明細（`classification_entries`）を書きます。

| kind | 画面の表示 | 入口 |
| --- | --- | --- |
| `import` | BOOTH 取り込み | ファイル、拡張、内蔵ブラウザからのインポート。対応リストの適用と辞書の整理を含む |
| `reclassify` | 再分類 | `extract_products`。バッチ末の再解決を含む。`note` に対象（`unclassified` / `stale` / `all`） |
| `catalog` | 対応表の再適用 | 設定の再適用、対応表の更新、初期データの復元 |
| `edit` | 手動編集後の再判定 | アバターの保存・削除・統合のあとの再解決 |
| `startup` | 起動時の整理 | DB を開いたときの辞書の整理 |
| `booth_detail` | 商品情報の更新 | 公開情報の取得で説明が変わり、分類がリセットされたとき |
| `undo` | 元に戻す | Undo そのもの |

- 記録は処理の前後で商品の状態を比べます（`observe` / `observe_all`）。カテゴリ、対応リンク、未収録の名前のどれかが変わった商品だけが明細になります。ジャンルだけの変更は明細になりません。
- 明細は「商品 1 つ × 実行 1 回」です。同じ実行の後の段階は同じ明細の変更後を更新し、最初の状態に戻ったら明細を消します。
- 変更が 1 件もない実行は行を残しません。
- 記録の失敗は標準エラーに出して続行し、分類は失敗させません。
- 手動の編集（カテゴリ、ジャンル、リンク、本体登録）は記録しません。記録するのは分類の適用経路だけです。
- 記録は端末内の表示用履歴です。同期の書き出しには含めず、分類の判断にも使いません。保持期間は無期限です。

## 画面

左メニューの「ログ」から「分類記録」タブ（`#/classification-log`）を開きます。

- 実行の一覧：日時、きっかけ、分類器、変更件数。行を開くと明細が出ます。
- 明細：商品名と ID、カテゴリとリンクの変更前 → 変更後、信頼度、未収録の名前。
- 商品で絞り込む：商品名の一部か商品 ID で、その商品の履歴だけを出します。商品カードの「⋯ → 分類記録を見る」は `#/classification-log/<商品ID>` を開きます。
- 未収録の名前：記録に残った名前を、関係する商品数とともに集約します。「一覧をコピー」で Issue に貼れる箇条書きをクリップボードへ送ります。取り消した明細の名前と、今は解決できる名前は出ません。v10 より前から残っている未収録名は、次に変更が記録されるまでここに出ません。

## Undo

明細 1 件を実行前の状態に戻します。カテゴリとリンクに加えて、ジャンル、抽出した名前、未収録の名前、汎用、信頼度、抽出日時、分類器の版、確認の印も `before_state` から戻します。再解決は抽出した名前からリンクを作り直すので、リンクだけ戻しても次の再解決で元に戻ってしまうためです。

Undo そのものも新しい実行（`undo`）として記録し、元の明細には Undo 済みの印を付けます。

次のときは戻せず、理由を画面に出します。

- その商品の今のカテゴリとリンクが、明細の変更後と一致しない（後の実行や手動編集で変わった）
- `links_locked` が立っている
- `category_locked` や `genre_locked` が立っていて、戻すと値が変わる
- 除外中、または商品が無い
- 元のリンク先のアバターが対応表から消えている
- すでに戻している、または Undo の記録そのもの

分類の実行中は Undo できません。実行中の明細はまだ書き換わるためです。

Undo は固定ではありません。戻した商品も、次の取り込み、再分類、起動時の整理で同じ分類が再度適用されることがあり、そのときは新しい記録が残ります。自動の分類から守りたいときは、商品を手動で編集して固定します。

本体登録の明細を戻すと、その本体だけが支えていた所持の印を外し、使われなくなった `owned-*` の仮アバターを消します。

## 確認キューから移したもの

- 商品の手動修正は「分類を編集」（`src/components/ProductEditDialog.tsx`）に移しました。商品カードの「⋯」と、インポートの「商品を管理・除外」の「編集」から開きます。変えた項目だけを送るので、触っていない項目は固定されません。
- 商品未設定のファイルの結び付けは、インポートの「手元のファイル」の折りたたみ（`src/components/UnlinkedFiles.tsx`）に移しました。
- 未分類の商品は、インポート画面の「2. 分類」の「未分類の商品を見る」か、「商品の管理」の「商品を管理・除外」の表示フィルタで探せます。

## 廃止したもの

- 確認画面（`QueuePage`）、ナビの件数バッジ、`list_queue`、「確認済みにする」（`ProductUpdate.confirm`）
- 新しいアバター候補の一覧、`avatar_candidates`、`register_avatar_candidate`、`alias_avatar_candidate`。名前の追加は対応表エディタで行います
- リンクの手動保存で未収録の名前を消す副作用
- 設定の「要確認の判定しきい値」。値は `settings.confidence_threshold` に残りますが、画面からは変えません

`products.needs_review` の列と計算は残しています。どの画面も読みません。分類改善用 JSON の `classificationStatus` だけが使います。`user_confirmed` も列として残し、対応表の本体、所有登録、公開終了の自動の確定を表します。旧キューで確認済みにした行の印も同じ意味のまま働きます。画面から立てる経路はありません。
