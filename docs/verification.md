## サイドバーからの遷移のもたつき（2026-11-14）

対象は main の `61a8dc1`（0.8.5）からの `04191b7`〜`b9ab215`。Linux x64 のコンテナ（Intel Xeon 2.1GHz、4 コア）、Rust 1.97.0、Node.js 22.23.4、Playwright の Chromium（ヘッドレス）で確かめた。Rust は Windows 配布版と同じ `codegen-units = 16`、`lto = "thin"` の release で測った。データは `nav_bench.rs` の合成ライブラリで、BOOTH のアカウント、実ライブラリ、Tauri の WebView には触れていない。

原因は3つあった。

- 一覧を読むたびに、全商品の購入した対応版を判定し直していた。バリエーション名を1つ照合するたびに、辞書の全アバター（同梱で923体）の名前と別名を正規化し直しており、300 商品でも1回の読み込みに約 0.9 秒かかった。
- アバター一覧・詳細とアセットの一覧を組み立てるとき、商品ごとに全行を探し、アバターごとに全商品を調べていた。2000 商品では、アバター一覧のカードの計算だけで 5.4 秒かかった。
- 一覧と件数のコマンドは同期で、UI スレッドで動いていた。読み込みの間はアプリ全体が止まり、離れた画面の読み込みも順に最後まで走って次の画面を待たせた。

各画面が呼ぶコマンドの時間（5 回の中央値、ミリ秒）。300 と 1000 は全商品をアセット更新の対象にした組、2000 は対象なしの組。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `library_stats` | 759 | 0.9 | 2786 | 3.1 | 5029 | 5.5 |
| `list_avatars` | 823 | 31 | 3766 | 107 | 10593 | 135 |
| `list_products_by_genre`（アセット） | 956 | 45 | 3067 | 176 | 6042 | 246 |
| `list_products_by_genre`（ワールド） | 956 | 41 | 2994 | 147 | 5683 | 221 |
| `get_avatar`（対応の多い1体） | 921 | 37 | 2977 | 159 | 5827 | 209 |

- 変更前と後で、7つのコマンド（上の5つと `asset_update_status`、`list_knowledge`）の出力 JSON を 300・500・1000・2000 商品の対象あり・なしの全組で突き合わせ、一時フォルダのパスを除いてすべて一致した。件数と商品の選択肢は、SQL で読んだ結果とスナップショットから作った結果が全組で一致した。
- 名前の索引は、同梱の全辞書について、名前・別名とそのゆれ（「版」「対応」「専用」、括弧、`-別名-`、大文字、`ver2`）で、変更前の走査と全辞書・絞り込みの両方の結果が一致することをテストで確かめた。
- 画面の切り替えは、変更前と後のフロントエンドの本番ビルドを Chromium で開き、上の計測で書き出した各版の出力を返し、測った時間だけ待たせる形で測った（一時的な計測用ビルドで、リポジトリには入れていない）。1000 商品・全商品を対象にした組で、サイドバーから順に開くと、アバター一覧の中身が出るまで 15.0 秒から 0.15 秒、アセット一覧は 7.3 秒から 0.25 秒になった。アセット一覧を開いたときの 50ms を超える処理は合計 806ms から 0ms になり、最初の 40 件のあとは描画のたびに足される。変更前は、画面を移るたびにサイドバーが更新確認の状態を読み直していた。変更後はその読み込みが無い。
- 同じ形で 1000 商品のアセット一覧を操作した。購入履歴などからのリンク（`#/assets/item/<ID>`）で 601 番目の商品を開くと、まだ描いていなかった分まで描いて枠で示し、表示域に入った。プレビューを開いて何も選ばずに ↑ を押すと、最初の 40 件しか描いていない時点でも最後の商品が選ばれてフォーカスが移り、もう一度 ↑ で 1 つ上へ移り、右パネルにその商品が出た。カードをドラッグするとジャンル列にワールドのジャンルが出て、離すと消えた。別のジャンルへ移ると最初の 40 件から描き直した。
- `cargo test --lib` 519 件成功、無視 3 件（この計測を含む）。`npm test` 285 件、`npm run build` が成功した。
- Windows の WebView2 での体感、実ライブラリでの時間、数 MB の応答を WebView に渡す時間、実際のマウスでのスクロール中に一覧が足される見え方は確かめていない。全商品をアセット更新の対象にしていると、商品カードの新着ファイル表示のために、一覧を読むたびに更新確認の保存値（1000 商品で 16.5MB）を読む（1000 商品で約 40ms）。この保存値の作りは変えていない。
