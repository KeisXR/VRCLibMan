# Unity プロジェクト連携（設計）

> **状態: 段階 1 と段階 2 を実装（2026-11-27）。段階 2 で残した小さなもの（[段階 2 で残したもの](#段階-2-で残したもの)）と、段階 3・4 は未実装の設計。** 実装した部分の契約は [AGENTS.md](../AGENTS.md) の「Unity プロジェクト」にある。未実装の部分は、実装したら書き直し、契約を足す（[実装時に AGENTS.md へ足す契約](#実装時に-agentsmd-へ足す契約)）。

いまの Unity 連携は、選んだ unitypackage を Unity の Import 画面へ渡すところで終わる（AGENTS.md「Unity で開く」）。渡したあと、アプリは結果を知らない。この設計は、Unity プロジェクトを**読むだけ**で次のことを見せる。

- どのプロジェクトがあり、どのアバターのものか（段階 1）
- どの商品がどのプロジェクトに入っているか（段階 2）
- 渡す前に、プロジェクトに足りないシェーダーやツールが無いか（段階 3）
- Unity の中からライブラリを見る（段階 4）

## 方針

- **プロジェクトのフォルダには書き込まない。** 読むのは一覧、版、パッケージの記録、`.meta` の GUID だけ。Unity が動かすファイルと競合しないため。
- **プロジェクトの作成・パッケージの追加と更新・バックアップ・移行はしない。** ALCOM / VCC の仕事で、複製しても価値が無い。足りないものは「ALCOM で追加する」と案内するだけにする。
- **ALCOM に無い価値は「プロジェクト × 自分のライブラリ」。** 段階 1 だけでは ALCOM の一部の複製なので、段階 1 は段階 2 の入れ物として薄く作る。
- **アバターへの着せ付け・配置はしない。** Modular Avatar などの領分で、失敗の責任を負えない。
- 判定は Rust に置き、言語モデルと外部通信を使わない。プロジェクトの名前とパスはログ・データ移行の ZIP・分類改善用 JSON に出さない。

## 段階 1: プロジェクトの一覧

### 一覧の出どころ

`src-tauri/src/unity_projects.rs`（`unity.rs` と同じ形: 純粋な解析関数 + `Sources` + `Os`）。出どころは 3 つで、id（下）で重複をまとめる。並びは ALCOM の一覧、次に DB の行。

1. **ALCOM / VCC**: `settings.json` の `userProjects`（パスの文字列の配列）。Windows は `%LOCALAPPDATA%\VRChatCreatorCompanion\settings.json`。Mac は `~/Library/Application Support/VRChatCreatorCompanion/settings.json`、Linux は `$XDG_DATA_HOME`（無ければ `~/.local/share`）の下にしているが、どちらも未確認。
2. **手動**: 利用者がフォルダを選んで足したもの（`unity_projects` 表の `manual`）。
3. **覚えているもの**: アバターと結び付けたときに残したパス。ALCOM の一覧から消えても出す。印も結び付けも無い行（結び付けたアバターを消したあと）は出さない。

Unity Hub の `projects-v1.json` は読まない（この PC では空で、形を確かめられていない）。

ALCOM の一覧は DB に写さず、画面を開くたびに読む（8KB のファイル 1 つ）。写すと ALCOM 側の追加・削除とずれるため。壊れた JSON、無いファイルは空として扱う（`unity.rs` と同じ）。BOM 付きの UTF-8 を受ける。

### プロジェクト 1 件から読むもの

フォルダに `Assets` と `ProjectSettings/ProjectVersion.txt` があるものだけをプロジェクトとする。

| 項目 | 読む場所 | 備考 |
| --- | --- | --- |
| 名前 | フォルダ名 | Unity の窓のタイトルと同じ |
| Unity の版 | `ProjectVersion.txt` の `m_EditorVersion` | `unity::is_unity_version` で検査 |
| 種類 | `vpm-manifest.json` の `dependencies` と `locked` | `com.vrchat.avatars` → アバター、`com.vrchat.worlds` → ワールド、両方無い → 不明 |
| パッケージ | 同じファイルの名前と版 | 段階 3 で使う。段階 1 では返すだけで、画面には出さない |
| 更新日時 | `Assets` フォルダの更新日時 | 並び順の手がかり。ALCOM の並びとは一致しない |
| 開いているか | 下の「開いているかの判定」 | |

読み取りは `library_files::wait_for` で 1 件 2 秒、全体 5 秒まで（`READ_TIMEOUT`・`LIST_TIMEOUT`）。切れた共有や外したドライブで画面を止めないため。時間切れは `state: "timeout"`（「確認できません」）、プロジェクトの形のフォルダが無いものは `"missing"`（「フォルダが見つかりません」）として一覧に残す。ALCOM の設定ファイルの読み取りも 2 秒まで。

プロジェクトの id は、パスから決める 16 桁の 16 進（FNV-1a 64 bit）。前後の空白・引用符・末尾の区切りを外し、Windows では `/` を `\` にそろえて大文字小文字を区別しない（`unity::dedupe_key`）。DB のキーとコマンドの引数に使い、コマンドは一覧にある id だけを受ける。並びは `Assets` の更新日時の新しい順。

### 開いているかの判定

- Windows: `unity_import::running_instances()` の `heading`（窓のタイトルの「 - Unity 」より前、`Project - Scene - Platform`）がフォルダ名で始まり、`version` がプロジェクトの版と一致するもの（`running: "open"`、`running_states`）。フォルダ名にも「 - 」が入り得る（`Avatar - Main`）ので、タイトルを「 - 」で区切った最初の部分とは比べない。1 つの窓に当てはまるプロジェクトが 2 つ以上あるとき（同じ名前と版、`Avatar` と `Avatar - Main`）はどれとも決めず、`"maybe"`（「開いているかもしれません」）とする。
- `Temp/UnityLockfile` は補助にも使わない（残骸が残るため）。
- Mac / Linux: 判定しない（「開いているか」を出さない）。

### プロジェクトを開く

`<Unity> -projectPath <フォルダ>` を引数の配列で渡す（シェルを通さない。作業フォルダと標準入出力は `-openfile` と同じ）。

- **プロジェクトの版とちょうど同じ版の Unity だけで開く**（`unity_projects::editor_for_open`）。`unity::status` の一覧（検出したものと、設定で手で選んだ既定の Unity）から `ProjectVersion.txt` と一致する版を探す。無ければ開かず、「このプロジェクトは Unity <版> で作られています。同じ版の Unity が見つからないので、ALCOM か Unity Hub で開いてください」と返す。違う版で開くと Unity がプロジェクトを変換し、元に戻せないため。既定の Unity も、版が違えば使わない。
- 開いている（`"open"`）と判定できたときは起動せず、`alreadyOpen: true` を返して画面が知らせる。`"maybe"` は起動する。
- 起動した子プロセスは待たない（Unity 本体なので終わらない）。起動に失敗したときだけエラーにする。
- メイン画面からだけ受ける（`unity_instances` と同じ検査）。
- 開く対象は、一覧に出ているプロジェクトの id だけ。任意のパスを受けない。

### 保存するもの（`library.sqlite` 版 16）

```sql
-- 手動で足したプロジェクトと、一覧から隠したプロジェクト。ALCOM の一覧は写さない。
CREATE TABLE unity_projects (
    id TEXT PRIMARY KEY,          -- パスから決めた 16 桁
    path TEXT NOT NULL,
    manual INTEGER NOT NULL DEFAULT 0,
    hidden INTEGER NOT NULL DEFAULT 0
);
-- アバターとプロジェクトの結び付け。本人が決めたものだけ。
CREATE TABLE unity_project_avatars (
    project_id TEXT NOT NULL REFERENCES unity_projects(id) ON DELETE CASCADE,
    avatar_id TEXT NOT NULL REFERENCES avatars(id) ON DELETE CASCADE,
    PRIMARY KEY (project_id, avatar_id)
);
CREATE INDEX unity_project_avatars_by_avatar ON unity_project_avatars(avatar_id);
```

関数は `src-tauri/src/db/unity_projects.rs`。結び付けを外す・隠すのをやめたときに、印も結び付けも無くなった行は消す（`prune_row`）。

- 多対多にする。1 つのアバターに複数のプロジェクト（この PC では Plum が 4 つ）、1 つのプロジェクトに複数のアバターがあるため。
- 行ができるのは、手動で足したとき、隠したとき、アバターと結び付けたときだけ。結び付けたときは、そのときのパスを `unity_projects` にも残す（ALCOM の一覧から消えても、どこのプロジェクトだったかを見せるため）。
- **データ移行の ZIP には含めない。** ローカルのパスであり、別の PC では意味が無い（`sync_export` の対象に足さない。テストで確かめる）。
- アバターの統合では、結び付けを同じトランザクションで統合先へ移し、重複を除く（購入した対応版と同じ）。
- 名前からの自動の結び付けはしない（フォルダ名 `Kip2` を Kipfel と読むような推測をしない）。段階 2 で「このプロジェクトにはアバター本体 X が入っています」と分かったときに、**候補として出す**だけにする。

## 段階 2: 導入済みの判定

### 考え方

unitypackage は gzip した tar で、中は `<GUID>/asset`・`<GUID>/asset.meta`・`<GUID>/pathname` の組が並ぶ（`unity_wrap.rs` が書いているのと同じ形）。Unity は取り込んだアセットの隣に、同じ GUID を書いた `.meta` を置く。したがって、

> パッケージの GUID の集合のうち、プロジェクトの `Assets` の `.meta` にあるものの割合

で「入っているか」が分かる。渡した記録は根拠にしない（Import 画面でキャンセルできるため）。

### パッケージの読み取り（`src-tauri/src/unity_index.rs`）

- 対象は、登録済みで除外していない商品のファイル（`product_files.local_path` と、結び付いた `local_files`）のうち、ライブラリかリモートライブラリの中の `.zip` と `.unitypackage`（`unity_index_jobs::sources`）。中にあるかは文字の上だけで比べ、届かない共有に触らない。単体のファイルを包んだもの（`unity_wrap`）は対象外。
- **ディスクへ取り出さない。** zip の項目を `zip` クレートのリーダーで開き、`flate2` の `GzDecoder` に渡し、512 バイトの tar ヘッダーを自前で順に読む（`tar` クレートは足さない）。ヘッダーの区切りで正しく終われば終わりとし、gzip が途中で切れていれば壊れているとする。
- 1 つの GUID について集めるもの:
  - `pathname` の 1 行目（4KB まで）。`Assets/` で始まらないものは捨てる。
  - `asset` の大きさ（tar ヘッダーの値。フォルダには `asset` が無い）。
  - **外への参照**（段階 3 の材料）: `asset` が 2MB 以下で先頭が `%YAML` のとき、本文の `guid: <32桁>` を拾う。パッケージ自身に含まれる GUID はあとで除く。1 つのパッケージで 10 万件まで（`MAX_REFS`）。
  - 入る場所のパスそのものは持たず、`Assets/` の下かどうかと拡張子だけを持つ。ダウンロードしたファイルを読むので、GUID の上限まで長いパスを並べたパッケージでメモリを使い切らないため。大きな項目の読み飛ばしも、期限を過ぎたらやめる。
- 上限: GUID 20 万件、展開後 16GiB、1 件 120 秒。超えたら「一部だけ読んだ」として、判定には使わない。tar の名前が `<32桁の16進>/<asset|asset.meta|pathname>` の形でない項目は読み飛ばす。
- 読むのは専用のワーカー 1 本（`unity_index_jobs.rs`、リモート自動同期と同じ形）か、プロジェクトを調べるコマンド。どちらも `unity_index_store::PASS` のロックを取ってから書く。ワーカーは起動の 20 秒後、内蔵ブラウザのダウンロードと拡張の自動整理の完了、フォルダスキャンと「ダウンロード済みファイルを登録」の完了で起き、まだ読んでいない・大きさか更新日時が変わったファイルを 1 件ずつ読む。`library.sqlite` のロックは対象を並べるあいだだけ持つ。分類・全取得・ダウンロードの最中は次のファイルの前で止め、60 秒おいて続きを読む。
- 進捗は `job-progress` の `unity-index`（「Unity パッケージを調べています n / m」）で、読むファイルがあるときだけ送る。
- 届かないファイル（切れた共有、登録に残っているが消えたファイル）は読まず、索引からも消さない。索引から消すのは、ライブラリの登録から無くなったファイルだけ（`unity_index_store::refresh`）。手元とリモートに同じ商品の同じ名前のファイルがあれば、手元のものだけを読む（`unity_index_jobs::pick_sources`。リモート自動同期で写したものを 2 回読まないため）。

### プロジェクトの読み取り

- `Assets` の下の `*.meta` を `walkdir` で歩き、先頭 256 バイトから `guid:` の行を読む。リンクはたどらない。上限 50 万ファイル、60 秒。打ち切ったとき、たどれないフォルダや読めない `.meta` があったとき（Unity が書き換えている途中など）は「途中まで」として、それまでに見つけた一致だけを出す（「入っていない」とは言わない）。
- **GUID の集合は保存しない。** 歩きながら索引（下の `package_guids`）を引き、パッケージごとの一致数だけを保存する。プロジェクト 1 つで数万件あり、全プロジェクト分を持つと DB が大きくなるため。
- 大きさの一致も数える: 一致した GUID の実ファイルの大きさが、パッケージの `asset` の大きさと同じか。同じ版かどうかの手がかりにする（下の「版」）。
- **遅いのはここ**である。計測では `.meta` 1 件を開くのに約 3 ミリ秒かかり、`Assets` だけで数秒〜十数秒になる（[計測](#計測)）。画面を止めずに裏で読み、進捗を `job-progress` に出す。前の結果があれば、読み直しの間もそれを見せる。
- 読むのは、本人がプロジェクトの詳細を開いたとき（結果が無いか古いとき、1 回だけ）と、「調べ直す」を押したとき（`scan_unity_project`）。索引を先に新しくしてから歩く。常駐の監視はしない。全プロジェクトをまとめて読むことも自動ではしない。結果には調べた日時を付け、画面に「◯分前に調べました」と出す。索引が変わったら前の結果を「古い」とする（`mark_index_changed`）。「Unityで開く」でパッケージを渡したプロジェクトが分かれば、その結果も古いとする（`mark_project_stale`。取り込まれたかもしれないため）。渡す先が決まったときに調べ直すことはしない（Import 画面を待たせないため）。
- **`Packages` はプロジェクトごとには歩かない。** `.meta` の多くは `Packages` の下にあり（計測では 4〜9 割）、毎回歩くと 20〜40 秒かかる。VPM パッケージは名前と版が同じなら中身も同じなので、`vpm-manifest.json` の `locked` にある「名前 + 版」ごとに 1 回だけ、どれか 1 つのプロジェクトの `Packages/<名前>/` を歩き（`vpm_scans`）、その GUID をすべて覚える（`guid_owners`。1 プロジェクトで数千件）。索引にある GUID だけを覚えると、ライブラリにファイルが増えるたびに歩き直しになるため。歩くのは、名前が英数字と `.` `-` `_` だけのもの（`vpm_folder_name`）。名前は `vpm-manifest.json` から来るので、区切りや `C:` のような名前で `Packages` の外を歩かないため。

### 保存するもの（`unity-index.sqlite`）

`library.sqlite` とは別のファイル `unity-index.sqlite` を、アプリのローカルデータ（`app_local_data_dir`）に置く。**消しても作り直せる写し**であり、利用者のデータではないため。データ移行にも含めない。長い読み取りの間に `library.sqlite` のロックを持たずに済む。版（`INDEX_VERSION`）が合わない・壊れているときは消して作り直す（移行を書かない）。表は `unity_index_store.rs` の `TABLES`。

| 表 | 中身 |
| --- | --- |
| `packages` | ファイルと zip の中の項目ごとに 1 行。大きさ・更新日時・商品 ID・ファイル数・打ち切っていないか・読めなかったか。unitypackage の無い zip と読めないファイルも、読み直さないよう印の行を残す |
| `package_guids` | GUID（16 バイト）・パッケージ・asset の大きさ（フォルダは NULL）・拡張子 |
| `package_refs` | asset の本文が指していた、パッケージの外の GUID（段階 3） |
| `project_packages` | プロジェクトとパッケージごとの、固有のファイルの数と一致数、いちばん多くを持つ VPM パッケージとその数、全体の一致数、編集されにくい種類の一致数と大きさの一致数 |
| `project_scans` | 調べた日時・最後まで歩けたか・古いか・歩いた `.meta` の数 |
| `guid_owners` | 歩いた VPM パッケージの GUID と、その持ち主の名前 |
| `vpm_scans` | 歩き終えた VPM パッケージの名前と版、`package.json` の `displayName` |

新しく読んだ・消したパッケージがあれば、調べた結果を古いとする（`mark_index_changed`）。`guid_owners` と `vpm_scans` はそのまま残す。ライブラリの登録から消えたファイルの行は、次の更新で消す。

索引は読むだけの呼び出し（プレビューの行など）でも開くので、表と版がそろっていれば開くときに何も書かない。調べている最中の索引へ、書き込みのロックを取りに行かないため。

### 判定の規則（`unity_index::verdict`）

数えるのは `asset` のある GUID だけ（フォルダの GUID は数えない。`Assets/<ショップ名>` のようなフォルダは、同じショップの別の商品と共有されるため）。

1. **固有の GUID**を先に決める: 索引の中で、ほかの**商品**のパッケージに現れない GUID。同じ商品の別バリエーション・別の版どうしの共有は固有として数える。
2. パッケージに固有の GUID が 1 つも無いとき（同梱のシェーダーだけ、など）は「判定できません」。
3. 固有の GUID の一致率で決める。

| 一致率 | 表示 |
| --- | --- |
| 80% 以上 | 導入済み |
| 5% 以上 80% 未満 | 一部が入っています（一致数 / 総数を添える） |
| 5% 未満 | 入っていません |

計測では、入れたプロジェクトは 100%、入れていないプロジェクトは 0% にほぼ分かれ、あいだに落ちたのは 54%（一部を消したと見られる）と 3%（35 件中 1 件だけの共有）の 2 例だった。この表はその 2 例を「一部」と「入っていません」に分ける。取り込んだあとに利用者がファイルを消す・移動するのは普通なので、100% は求めない。移動しても GUID は変わらないので、場所は見ない。

**同梱の共通パッケージ**は別に扱う。商品の zip には、古い lilToon などの unitypackage が同梱されていることがある（計測では `lilToon_1.4.0.unitypackage`）。その GUID は VPM 版の lilToon と同じなので、`Assets` には無くても、プロジェクトには同じものが `Packages` に入っている。

- パッケージの GUID の 80% 以上を 1 つの VPM パッケージが持っているとき（`guid_owners`）、そのパッケージを「<VPM パッケージ名> の同梱版」とする。
- 同梱版でないパッケージでも、VPM パッケージが持っているファイル（少しだけ同梱されたシェーダーなど）は固有のファイルに数えない。VPM 版を入れたプロジェクトでは `Assets` に無く、一致率を下げるため。
- 持ち主が分かるのは、その VPM パッケージを入れたプロジェクトを 1 度でも調べたあと。それまでは、同梱版が `Assets` に取り込まれていれば、ふつうのパッケージとして「導入済み」になる（その商品だけが同梱しているとき）。
- 同梱版は商品の「導入済み」の判定に数えない。
- プロジェクトにその VPM パッケージが入っているとき、同梱版には「このプロジェクトには <名前> が入っています。取り込む必要はありません」と出す（段階 3 の画面）。同じ GUID のものを重ねて取り込むと、シェーダーが壊れる原因になるため。

商品の単位では、同梱版を除いたパッケージのうち、いちばん強い判定を商品の判定にする（導入済み > 一部 > 入っていません > 判定できません。`product_verdict`）。同梱版しか無い商品だけが「同梱版」になる。どのパッケージ（どのアバター向け）が入っているかを添える。ファイルが 1 つも無いパッケージ（unitypackage の無い zip の印など）は並べない。

### 版

GUID は版が変わっても同じなので、GUID だけでは「どの版か」は分からない。次の範囲に留める。

- 同じ商品の導入済みのパッケージが 2 つ以上あるとき（アセット更新の「以前のファイル」など）: 大きさの一致率がいちばん高いものに「入っている版の見込み」と出す（`PackageInstall.closest`）。比べるのは、編集されにくい種類（`STABLE_EXTENSIONS`: fbx・png・psd・tga・jpg・jpeg・dll・cs・shader）だけ。マテリアルや prefab は利用者が編集するため。一致率が 0 なら何も付けない。
- 「入っている版」が、その商品の「新しいファイル」より古いとき、プロジェクトの詳細に「新しいファイルがあります」と出す（まだしていない）。
- 手元に版が 1 つしか無いときは、版については何も言わない。「新しい」「古い」を大きさだけから推測しない。

### 画面

実装したもの:

- **プロジェクトの詳細（`#/projects/<id>`、`src/pages/ProjectDetailPage.tsx`）**: プロジェクトの一覧とアバター詳細の行から名前を押して開く。上に名前・種類・版・結び付けたアバター・「開く」・「調べ直す」、その下に調べた日時（調べている間は「照らし合わせています。書き換えません」）。途中までしか歩けなかったときは「ここに無い商品も、入っていないとは限りません」と出す。
  - 「入っている商品」（件数付き）: 1 行 1 商品で、サムネイル・題（アプリの中の行き先へのリンク。規則は購入履歴の `library_link`）・パッケージごとの判定と「n / m ファイル」・「入っている版の見込み」の印。題の順。
  - 「一部が入っています」: 説明を添えて同じ形で。
  - 「同梱されていた共通パッケージ」「判定できない商品」: 折りたたみ。
  - 入っていない商品は並べない（ライブラリ全部が並ぶため）。
  - 調べている間に別のプロジェクトへ移ったら、遅れて届いた結果は捨てる。索引か結果が変わった知らせ（`unity-index-changed`）で結果を読み直す（調べ直しはしない）。プレビューの行も同じ知らせで読み直す。
- **プレビュー欄（右パネルの「プレビュー」タブ）**: 「プロジェクト」の行に、選んだ商品が入っている（導入済みか一部）と分かったプロジェクトの名前を並べ、押すとプロジェクトの詳細へ（`product_unity_installs`）。調べたプロジェクトが 1 つも当たらなければ行ごと出さない。調べたあとに索引が変わって「古い」となったプロジェクトの結果は使わない（パッケージの GUID が変わったかもしれないため。調べ直すまで何も言わない）。
- 印の文言は「導入済み」。調べていないプロジェクトについては何も出さない（「未導入」と出さない。拡張の「未登録を非対応と判断しない」と同じ考え方）。

- **プロジェクトの詳細の「まだ入っていない対応アセット」**: 結び付けたアバターに対応していて、入っていないと分かった商品（`unity_project_suggestions`、Rust の `project_suggestions`）。対応はアバター詳細と同じ組み立て（`load_avatar` のジャンルの節）で、判定が「入っていません」の商品だけを入れる。手元にファイルが無い商品は索引に無く判定できないので入れない。手元にファイルがある順に、商品カード（`ItemCard`、ファイルの行に「Unityで開く」）で並べる。折りたたみで、30 件ずつ。
- **入っているアバター本体の結び付けの候補**: 導入済みの商品のうち、行き先がアバター（本体）で、そのアバターをまだ結び付けていないとき、「このプロジェクトに「<商品名>」が入っています」と「結び付ける」を出す（`bodySuggestions`）。名前などから推測せず、本人が押したときだけ結び付ける。
- **アバター詳細の「導入済み」の印**: 商品カードに、結び付けたプロジェクトのうち 1 つについて「導入済み」「一部導入済み」の印を出す（前に調べた結果から。調べていなければ出さない）。2 つ以上結び付けているときは、「Unity プロジェクト」の行の「「導入済み」の印:」で選ぶ（画面の中だけで、保存しない）。
- **「Unityで開く」の「このプロジェクトには入っています」**: 渡す先のプロジェクトが分かり（Windows で窓を選んだとき、または起動中の Unity が 1 つのとき。窓の見出しと版で 1 つに決まるときだけ）、その商品が導入済みと分かっていれば、渡す前に知らせ、「もう一度渡す」「やめる」を出す（`unity_install_check`）。止めはしない。

### AI エージェント連携（MCP）

読むだけのツールを 1 つ足す。Unity を操作しているエージェントは自分の作業フォルダを知っているので、相性が良い。

- `unity_project`（実装済み）: 引数 `project` はプロジェクトのフォルダか名前（名前は 1 つに決まるときだけ）。一覧にあるプロジェクトだけ受ける（`commands::agent_project`）。返すのは、プロジェクトの名前・版・種類・結び付けたアバター、入っている商品（`installed` に導入済みか一部か）、まだ入っていない対応アセット（`notInstalledCompatible`、画面の候補と同じ）、調べた日時。商品の形は既存のツールと同じ（`Facts::item`）で、除外した商品と R-18 の扱いも同じ（`mcp_api::unity_project_reply`）。パスは返さない（手元のパスは既存の `product_files` で取る）。
- 呼ばれたときに調べ直しはしない。調べていない・古い・途中までのときは `note` で伝え、VRCLibMan の「プロジェクト」で調べてもらうよう書く。プロジェクトの一覧と索引は、受信口がデータベースのロックを外してから読む（`Reply::UnityProject`）。

### テスト

- `unity_index.rs`: GUID の読み書きと標準の GUID、tar の読み取り（ファイル・フォルダ・`Packages/` を捨てる・拡張子）、外への参照（自分の GUID と標準のものを除く）、壊れた gzip と途中で切れたもの、期限での打ち切り、zip の中の複数のパッケージ、`.meta` の読み取りと上限、判定の表（計測の 54% と 3% の例を含む）と商品の判定。

## 段階 3: 必要なシェーダー・ツールの確認

### 考え方

**説明文は読まない。パッケージの中身から決める。** 説明文の「必須」「推奨」「対応」の書き分けを規則で読み分けるのは難しく、間違えると利用者を誤らせるため。

マテリアルは `m_Shader: {fileID: …, guid: …}`、prefab のコンポーネントは `m_Script: {…, guid: …}` で、使うシェーダーとスクリプトを GUID で指す。その GUID がパッケージ自身に入っていなければ、**外にある何か**を必要としている。段階 2 の読み取りが、これを `package_refs` に集めている。

その GUID が何のものかは、利用者のプロジェクトから覚える: `Packages/jp.lilxyzw.liltoon/` の下の `.meta` にその GUID があれば、持ち主は `jp.lilxyzw.liltoon`（`guid_owners`）。どのプロジェクトでも見たことが無い GUID は「分からない」とし、不足とは言わない。

- 利点: 対応する道具の表を持たず、lilToon でも Modular Avatar でも、利用者が 1 度でもどこかのプロジェクトに入れていれば分かる。
- 持ち主がライブラリの別の商品のこともある（unitypackage で配られるシェーダーなど）。`package_guids` を引けば「この商品には <商品名> が必要です」と言える。

### 判定

渡す先のプロジェクトが分かるとき、パッケージの外への参照を持ち主ごとにまとめ、

- 持ち主が VPM パッケージ → そのプロジェクトの `vpm-manifest.json`（`locked`）か `Packages/<名前>/` にあるか。
- 持ち主がライブラリの商品 → 段階 2 の判定で導入済みか。
- 無いものだけを「このプロジェクトに無いもの」として出す。

言えるのは**有るか無いか**だけ。必要な版（lilToon 1.8 以上、など）は中身から分からないので言わない。Unity に標準で入っているシェーダー（GUID が `0000000000000000f000000000000000` など）は無視する。

表示する名前は VPM パッケージの名前そのまま（`jp.lilxyzw.liltoon`）から始める。読みやすい名前（lilToon）が要るなら、`Packages/<名前>/package.json` の `displayName` を読んで `guid_owners` と一緒に覚える。

### 画面

- 「Unityで開く」のダイアログ: 渡す先が分かり、無いものがあるとき、「このプロジェクトに無いもの: lilToon、Modular Avatar。ALCOM で追加してから取り込むと、マテリアルが正しく表示されます」。渡すボタンは押せるまま。
- 同じダイアログで、zip の中の同梱版（段階 2 の「同梱の共通パッケージ」）は、プロジェクトに同じ VPM パッケージがあるとき選択を外して出し、理由を添える。本人が選べば渡せる。
- プロジェクトの詳細: 「入っているパッケージ」の一覧（名前と版）。
- 商品カードには出さない（プロジェクトが決まらないと言えないため）。

### 実装前に確かめること

- マテリアルのシェーダーについては計測で確かめた（アバター本体 3 件と乗り物 1 件は `jp.lilxyzw.liltoon` に当たった）。prefab のスクリプト（Modular Avatar など）への参照はまだ見ていない。
- 持ち主が `com.vrchat.base` の参照があった（VRChat SDK のシェーダー）。どのプロジェクトにも入っているものを「必要なもの」に並べるかは、実データを見て決める。
- 持ち主の分からない参照のうち、Unity に標準で入っているものの GUID の形を確かめ、無視する一覧を作る。
- アバター本体のあとに入れる衣装は、アバター本体の GUID（メッシュ、アーマチュア）を参照していることがある。これが取れれば「先にアバター本体 <名前> を入れてください」も同じ仕組みで言える。段階 2 の索引で確かめられる。

## 段階 4: Unity のエディタ拡張

Unity の中に VRCLibMan の窓を出し、いま開いているプロジェクトに合う商品を並べ、押すと取り込む。価値は高いが、C# の保守と配布が増えるので、段階 2 の反応を見てから決める。先に決めておくのは境界だけ。

- **配布**: VPM のパッケージにし、利用者が ALCOM で自分のプロジェクトに足す。アプリはプロジェクトへ書き込まない、という方針を変えない。
- **通信**: 既存の受信口 `127.0.0.1:17321` に `/unity/` を足す。`/mcp/` と同じ条件（`Origin` のある要求は 403、設定でオンのときだけ、専用のコードを Bearer で）。コードは `mcp-token` と同じ置き方の別ファイルにし、拡張はそれを読む。
- **判定は Rust に残す**: 拡張は `AssetDatabase` から得た GUID を送るだけにし、導入済みかどうかは `unity_index::verdict` が決める。外から `.meta` を歩くより正確で速いが、規則は 1 か所に保つ。
- **取り込み**: `AssetDatabase.ImportPackage(path, true)` で Import 画面を出す。確認なしの取り込みはしない。zip の中のパッケージは、アプリに取り出しを頼む（既存の `prepare_unity_packages` と同じ場所と検査）。
- **ダウンロード**: 拡張からは始めない。アプリで「ダウンロード」を押す。

段階 2 と 3 のデータと規則がそのまま土台になる。エディタ拡張のために別の判定を作らない。

## 実装時に AGENTS.md へ足す契約

実装した段階のものだけを、1〜3 文と参照で足す。段階 1 は足した（AGENTS.md の「Unity プロジェクト」と「続けて作らないもの」）。

- 段階 1（済み）
  - 「続けて作らないもの」に、Unity プロジェクトの作成・パッケージ管理・バックアップ（ALCOM の領分）を足す。
  - Unity プロジェクトのフォルダには書き込まない。読むのは一覧・版・`vpm-manifest.json`（段階 2 から `.meta`）だけ。
  - プロジェクトは、版がちょうど一致する Unity でだけ開く。違う版で開くと変換され、戻せないため。
  - `unity_projects`・`unity_project_avatars`（DB 版 16）はデータ移行の ZIP に含めない。名前からアバターとの結び付けを推測しない。
  - 「Unity で開く」の節の「プロジェクトに書き込まない」は、受け渡しについての記述のまま残す。
- 段階 2（中核は済み）
  - 導入済みの判定は GUID の一致だけで決め、渡した記録を根拠にしない。調べていないプロジェクトについて「入っていない」と出さない。
  - `unity-index.sqlite` は作り直せる写しで、`library.sqlite` の移行の対象にしない。パッケージはディスクへ取り出さずに読む。
  - 判定は `unity_index::verdict` の 1 か所。画面・MCP・（段階 4 の）拡張に複製しない。
- 段階 3
  - 必要なものは、パッケージの中の参照と、利用者のプロジェクトで見つけた持ち主だけから言う。説明文から推測しない。持ち主の分からない参照を不足と言わない。版は言わない。

## 計測

2026-11-27、Windows 11、作業ブランチ `claude/unity-loose-files`（`d07c3ca`）の時点。アプリのコードではなく、同じ読み方をする Python のスクリプトで測った（読むだけ）。Rust の実装の速さを測ったものではない。ほかの処理が動いている PC での 1 回の計測である。

**パッケージの読み取り**（ライブラリの zip 13 件の中の unitypackage 13 件、zip → gzip → tar を取り出さずに読む）

| 大きさ（gzip） | 展開後 | 時間 | GUID |
| --- | --- | --- | --- |
| 326MB | 623MB | 1.2 秒 | 61 |
| 92MB | 94MB | 0.2 秒 | 27 |
| 68MB | 90MB | 0.2 秒 | 290 |
| 56MB | 80MB | 0.2 秒 | 215 |
| 37MB | 84MB | 0.2 秒 | 653 |

13 件の合計で 3 秒未満。GUID は 1 件あたり 27〜653。パッケージ側は速く、裏で読んでも負担にならない。数 GB のパッケージは手元に無く、測っていない。

**プロジェクトの読み取り**（26 件。`Assets` と `Packages` の両方の `.meta` を開いて GUID を読む）

- 1 件あたり 5〜43 秒、`.meta` は 2,100〜11,400 件。1 秒に約 300 件で、ファイルを開く時間が大半だった。
- `Assets` の下は 58〜4,900 件で、全体の 3%〜6 割。残りは `Packages` の下。
- 同じ割合なら `Assets` だけで 0.2〜16 秒。2 回目以降は OS のキャッシュで速くなる可能性があるが、測っていない。

**一致**

- 入れてあるプロジェクトでは、パッケージの GUID の 100% が見つかった（アバター本体 3 件、そのほか 8 件）。入れていないプロジェクトでは 0%。
- あいだの値は 2 例: 79 件中 43 件（54%）と、35 件中 1 件（3%）。
- 一致したファイルの場所は、パッケージの `pathname` とほぼ同じだった（移動は 0〜2 件）。
- 大きさはおおむね 8 割以上が同じで、違うものが 1 プロジェクトあたり 0〜49 件あった。利用者が編集したものと見られる。版の比較に使うなら、編集されにくい種類に絞る必要がある。
- 商品の zip に同梱された `lilToon_1.4.0.unitypackage` は、20 件のプロジェクトで 98% が `Packages` の下に見つかった。`Assets` だけを見ると「入っていない」になる。

**参照の持ち主**（マテリアルが指すシェーダーのうち、パッケージ自身に無いもの）

- アバター本体 3 件と乗り物 1 件: すべて `jp.lilxyzw.liltoon`（2〜4 件）。
- ワールド用ギミックなど 6 件: 持ち主の分からないものが 1〜2 件。うち 2 件は `com.vrchat.base` も 1 件。分からないものは Unity の標準のシェーダーと見られるが、確かめていない。

## 決めたこと

2026-11-27 に、すべて「決めたこと」の側で進めると決めた。別の選び方は、見直すときのために残す。

| 点 | 決めたこと | 別の選び方 |
| --- | --- | --- |
| 左サイドバーの「プロジェクト」を常に出すか | 常に出す。プロジェクトが無いときは追加の案内を出す | プロジェクトが 1 つも見つからない間は出さない |
| 右パネルにタブを足すか | 足さない。段階 2 で「プレビュー」タブに節を足す | 「プロジェクト」タブを足し、一覧を見ながら導入状況を出す |
| 開いたあとの受け渡しを自動で続けるか | 続けない。本人がもう一度押す | Unity の窓が出るまで待って渡す（待ち時間が読めず、失敗の見せ方が難しい） |
| Unity Hub の一覧を読むか | 最初は読まない（形を確かめられていない） | 項目のある `projects-v1.json` を入手して読む |
| プロジェクトをいつ調べるか | 詳細を開いたとき・渡す先が決まったときに、そのプロジェクトだけ（1 件で数秒〜十数秒） | 起動時に全プロジェクトを裏で調べる（一覧にすぐ印が出るが、26 件で数分ディスクを読み続ける） |
